TRACER

Chat with an AI model that inspects Docker, Swarm, Kubernetes, this
host and your app source code. It looks freely, and changes something
only after you type yes. It never runs shell commands.

START

  docker compose up -d     start it (once)
  ./ts check               test every connection
  ./ts                     chat

COMMANDS

  ./ts                     chat
  ./ts check               test Docker, contexts, logs, the model
  ./ts watch               watch health; speak only when it changes
  ./ts tools               list every tool it can use
  ./ts setup               make the keys for several hosts (once)
  ./ts user add NAME       an account for the web page
  ./ts --help              this guide

IN THE CHAT

  /context                 list contexts (* = active)
  /context NAME            switch context, this chat only
  /paste                   paste many lines; finish with /end
  /report                  write this chat up as an incident report
  /case                    save this problem and its fix for later
  /tools                   list every tool
  /new                     forget this conversation
  /help                    short list of these
  /quit                    leave (Ctrl-D too)
  Ctrl-C                   stop the current answer

Follow-up questions keep the conversation going.

WHAT TO ASK

Whole system
  What needs attention on this host?
  Check every context and tell me what is broken.

Containers
  Why is web-1 unhealthy?
  Why did worker-2 restart last night?
  Was db-1 killed for running out of memory?
  Can web-1 reach db-1 on port 5432?

Docker engine
  What storage and logging drivers is the engine using?
  What is filling the Docker disk?
  Which volumes does nothing use?
  Which containers use the image python:3.13-slim?

Swarm
  Why is the service api short of replicas?
  Which nodes are down?

What changed
  It worked this morning. What changed since then?
  What changed in the last 2 hours?

Kubernetes
  Why is my pod stuck in Pending?
  Why does api keep crashing? Check the previous run's logs.
  Why can't anything reach the service web in namespace shop?
  Can pod web-1 reach db.shop on port 5432?
  Show errors from all pods of deployment web, last 30 minutes.
  Switch to vks-b and show me warnings from the last hour.

Host
  Why is the load high?
  Has the kernel killed anything today?
  Is anything listening on port 8080?
  Is the VPN tunnel up?

Applications and code
  web-1 crashes at start. The source is in /apps/web. Find the bug.
  Where is the setting db_timeout used in /apps/web?
  This stack trace is from api. Which line is wrong? (use /paste)

APPROVING A FIX

For a change, it stops and shows:

  == Approval needed ==
  Action:  Restart container web-1
  Why:     ...
  Command: docker restart web-1
  Type yes to run it, anything else to skip:

Only yes runs it. Check the cluster name on Kubernetes fixes.
Fixes it can make: restart, start and stop a container; restart and
scale a Swarm service; delete a pod; restart and scale a Kubernetes
workload.

COMMANDS IT ASKS YOU TO RUN

For anything its tools can't reach, it gives you commands to run
yourself, then you paste the result back:

  you> Is the firewall blocking port 443?
  ...
  sudo iptables -L -n | grep 443
  Paste the output with /paste.

  you> /paste
  Paste now. Finish with a line saying /end
  (paste the output)
  /end

Nothing checks these commands, and approval does not cover them.
Read each one first. Any that changes something should start with
"WARNING, changes the system:", but the model can get this wrong.

KUBERNETES CONTEXTS

It uses your kubectl login, so log in as usual first:

  kubectl config use-context vks-a
  ./ts

The prompt shows the active context:

  you [vks-a]> /context
  * vks-a: ok
    vks-b: the login was refused: the token has expired or is wrong.
    sup-ns: ok, supervisor (manages VKS clusters)
  you [vks-a]> /context vks-b
  Active context is now vks-b. Your kubeconfig was not changed.

You can also just ask: "switch to vks-b". Switching never changes
your kubeconfig or other terminals. If a login expires, log in again
in another terminal; the chat carries on. New contexts appear the
next time you run ./ts.

WHAT CHANGED

Most faults follow a change. While a chat or ./ts watch is open, the
state is written down every 5 minutes: images, replica counts,
restarts, nodes, configmap versions, containers, and on VKS the
machines and VMs. Ask "what changed in the last 2 hours?" and it
compares then with now, and adds the rollouts and restarts the cluster
itself recorded.

  - Docker is recorded all the time, in the background. Kubernetes
    is recorded only while a chat or watch is open, because your
    login exists only then. Leave ./ts watch running to always
    have a Kubernetes history.
  - Snapshots are in the log folder, under snapshots/. They are
    compressed, kept 7 days, and the folder never passes 50 MB: the
    oldest go first. They hold names, images, counts and states: no
    settings values, no Secrets.

WATCH

  ./ts watch               check every 60 seconds
  ./ts watch --every 300   check every 5 minutes

Checks the host, Docker, Swarm, every context and, on VKS, the
clusters a Supervisor manages. No model is used. It prints the open
problems once, then only what is NEW or OK AGAIN:

  09:14:02 NEW       docker: web-1: Exited (1) 5 seconds ago
  09:20:02 OK AGAIN  docker: web-1: Exited (1) 6 minutes ago

Ctrl-C stops it. A cluster login that expires shows as a problem: log
in again in another terminal, and start ./ts watch again to pick up
new contexts.

REPORT

In a chat, /report writes up what was found: summary, timeline,
evidence, cause, fix, still unknown. It is shown and saved in the log
folder under reports/. A model wrote it: check it before passing it on.

CASES

When a problem is solved, type /case. The model writes a short note:
symptom, cause, fix, how to recognise it next time. You read it and
type yes to keep it. Later chats search these notes first, and still
confirm against the live system: a case is a lead, not proof.

  - Saved in runbooks/_cases/<host>/ when you leave the chat, so
    every host that runs from this folder sees it.
  - To correct a case, edit its file. To remove one, delete the file.
  - ./ts check shows how many are saved.

VMWARE VKS

A context marked "supervisor" is where VMware keeps each VKS cluster,
its machines and their VMs. Ask from any context:

  Why is node prod1-w-2 missing?
  Is the upgrade of cluster prod1 stuck?

  Why is the claim data in namespace shop stuck Pending?
  Pod db-0 is stuck in ContainerCreating. Is it the volume?
  Are there any volume problems?

It finds the Supervisor context itself and lists only what is not
ready, with VMware's reason (e.g. no host has enough memory, or a
storage limit that is full). For a volume it follows the claim from
the pod down to VMware's side. It does not switch your context.
Nothing is ever changed on a Supervisor: the fix tools refuse it. No
Supervisor in the list: log in to it with kubectl, then run ./ts again.

SEVERAL HOSTS

Every host runs the same code from the same folder. One is the hub;
the others are agents that answer the hub about themselves.

  hub      serves the web page, watches Kubernetes once for
           everyone, and can look at the other hosts
  agent    answers the hub on agent-port with its own Docker,
           host and app files. It looks only: no fixes, no
           Kubernetes, no shell.

Set up, once:

  1. In compose.yaml: hub-host and agent-hosts, as the command
     "hostname" prints them on each host.
  2. ./ts setup            (on any one host; the folder is shared)
  3. docker compose up -d  (on every host)
  4. ./ts check            (on the hub: every agent should answer)

./ts setup writes a shared key and a certificate key to .env, and
the certificate to certs/. They are never shown. Traffic between
hosts is encrypted, and an agent answers only the hub.

On the hub, ask about any host:

  Why is relay unhealthy on host-02?
  Which hosts have a container that isn't running?

./ts on an agent host sees only that host. Fixes work only on the
host you are typing on.

WEB PAGE

The hub serves a page at https://<hub host>:<web-port>.

  ./ts user add NAME       add an account (asks for a password)
  ./ts user remove NAME
  ./ts user list
  docker compose up -d     on the hub, after any of these

The page looks only: it never changes anything. Fixes stay in ./ts.

  Trace          the chat, drawn as a trail: symptom, evidence,
                 cause, fix. Select a step to see its full output.
  Map            each host's containers as squares, and each
                 cluster; select a square for its logs and changes.
                 Open problems are listed beside it.
  What changed   one lane per host and cluster: changes, problems
                 and gaps in recording. Pick some to trace together.
  Console        a status wall: problem count, last hour per host,
                 live feed. Full screen for a big monitor.
  Library        cases, runbooks and reports; cases can be edited
                 and deleted

"Trace this" on the Map, and "Trace these" in What changed, open
the Trace with the question written and the host chosen.

AUTO-TRACE AND CHANGE LINKS (on the hub)

When the watch finds a new problem, the hub writes down the state
at once and looks for a change just before it on the same host or
cluster (link-minutes, default 10):

  linked   the change names the same container or workload
  maybe    same host, other name: worth a look, not a cause

A restart, a state flip or fewer ready is never a cause: that is
what the problem looks like. The link shows on the Map, in What
changed (a line between the two) and in the Console.

Then Tracer traces the problem itself, look-only: what changed,
logs and state, past cases, then Cause: and Fix:. It uses the
learn model when one is set. The Map shows "Traced, likely: ..."
with Open trace; everyone signed in can read it and ask more.
At most auto-trace-per-hour (default 10); auto-trace "off" stops it.
Problems already open when the page starts are not traced.

A case saved, edited or deleted on the page counts on the hub at
once. The other hosts see it after ./ts next runs on the hub.

The certificate is our own, so a browser warns the first time. To
use one from your own CA for the page:

  ./ts setup --web-cert CERT.pem KEY.pem
  docker compose up -d     on the hub

Both files in PEM form; the key without a passphrase; the hub's
name, as typed in the browser, in the certificate. It is copied to
certs/web-cert.pem and its key goes to .env. Hosts still talk to
each other with the certificate ./ts setup made. To go back:
./ts setup --web-cert remove. ./ts check says when either
certificate runs out.

Accounts are kept in .env as hashes, never as passwords.

DOCKER ONLY

Set kubernetes: "off" in compose.yaml, then docker compose up -d.
No cluster tools, no kubectl proxies, and nothing about clusters in
check, watch, what changed or the page.

SOURCE CODE

It can search and read code under the folders in file-roots, in
compose.yaml (default /apps and /apps2). To add a folder:

  1. add it to file-roots in compose.yaml
  2. docker compose up -d

It reads code but can't edit or run it. It shows a fix as a diff for
you to apply. It skips .env, key files, links, .git and node_modules.

RUNBOOKS

A runbook is a page of notes on one app: what it depends on, its
ports, logs, errors and what to check first. Chat reads it whenever
that app comes up. To draft one, run this on the host that has the app:

  ./ts learn /apps/myapp

It reads the app's key files, adds what is running now, and saves
runbooks/<this host>/myapp.md. Each host has its own folder, so hosts
sharing this install never overwrite each other. Chat prefers this
host's runbooks and can read the others.

Each fact names its file:line. The model must quote the words a fact
came from, and a fact whose words aren't in the file is dropped. That
proves the words exist, not that the model understood them, so check
the draft. Then:

  1. fix anything wrong, and fill in Your notes
  2. change the line "Status: DRAFT" to "Status: REVIEWED"

Chat treats a draft as unconfirmed. Running learn again replaces a
draft, but refuses a reviewed runbook unless you add --force. --force
keeps the old one as myapp.md.bak.

learn skips .env, key files, tests, backups and logs, and masks
secrets before the model sees them. The folder must be in file-roots.

SETTINGS

In the block at the top of compose.yaml. After a change, run
docker compose up -d. Secrets go in .env.

  llm-url, llm-model   the model server, usually ending in /v1
  llm-verify-tls       check the model server's certificate: true/false
  llm-ca-file          private CA for that check, e.g. /certs/ca.pem
  llm-reasoning        thinking: off, low, high, or empty
  llm-max-tokens       largest reply
  allow-changes        false = look only, the fix tools disappear
  protected-names      never changed, even if approved
  file-roots           folders it may read and search
  max-steps            most model rounds for one question
  max-seconds          most time for one question
  learn-max-files      most files ./ts learn reads per app
  learn-minutes        most time ./ts learn takes per app
  learn-llm-url        another model server for ./ts learn; empty
  learn-llm-model      = same as the chat. ./ts check tests it.
  record-minutes       background snapshots of Docker, with no
                       chat open; 0 = off
  kubernetes           off = Docker and host only
  hub-host             the host that serves the page and looks at
                       the others; empty = this host stands alone
  agent-hosts          the other hosts, separated by commas;
                       name=address if a name does not resolve
  agent-port           port the agents listen on (8001)
  web-port             port of the web page (9001)

  LLM_API_KEY in .env  the model's key; empty for vLLM
  LEARN_LLM_API_KEY    in .env: the learn model's key, if its
                       server needs one. The chat's key is never
                       sent to another server.
  AGENT_KEY, TLS_KEY   in .env: written by ./ts setup
  WEB_TLS_KEY          in .env: written by ./ts setup --web-cert
  WEB_USERS            in .env: written by ./ts user add

WHEN SOMETHING IS WRONG

  Cannot reach the model server
      Check llm-url in compose.yaml.
  The model server refused access
      Check LLM_API_KEY in .env, then docker compose up -d.
  Not found (HTTP 404)
      Check llm-url and llm-model.
  The model server's certificate failed the check
      Put its CA in ./certs and set llm-ca-file, or set llm-verify-tls
      to "false".
  The model server rejected tool calling
      Turn on tool calling for the model on its server.
  The login was refused
      Log in again with kubectl.
  Skip on Kubernetes in ./ts check
      kubectl isn't working on this host, and ./kube is empty.
  Answer cut off
      Raise llm-max-tokens.
  The conversation is too long
      Type /new.
  Not running, or "service is not running"
      docker compose up -d
  An agent did not answer
      On that host: docker compose up -d, then ./ts check there.
  An agent refused: not the hub's address
      The hub has several addresses. Write hub-host as name=address.
  The encrypted connection failed
      Both hosts need the same certs/ folder and the same .env.
  The web page is not served
      ./ts user add NAME, then docker compose up -d on the hub.

FILES

  logs/<date>.log    what happened, with every approval and decline,
                     what the hub asked an agent, and who signed in
  kube/              optional service-account logins, one per cluster
  README.md          design and air-gapped install

SAFETY

  Passwords, keys and tokens are masked before the model, the screen
  or a log sees them. This works by pattern, so it can miss some.
  Kubernetes Secrets, .env and key files are never read.
  Logs may hold hostile text; the model is told to treat it as data.
  The model can be wrong. Check its evidence before you approve.
  Anyone who can run ./ts has Docker admin rights.
  Anyone with a page account can read what the hub's logins can see,
  on every host and cluster. The page can't change anything.
